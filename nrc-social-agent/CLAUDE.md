# CLAUDE.md

## What this project is

NRC Social Agent is a private, AI-powered social-media publishing assistant for NRC. It automates the workflow of turning raw uploaded media into a published social post: ingest → analyze → converse → generate copy/metadata → preview → approve.

Version 1 targets Telegram only. The product is designed so that additional platforms (Instagram, LinkedIn, Threads) can be added later as adapters, without redesigning the core.

See the other permanent docs in this directory for detail:

- [PRODUCT.md](PRODUCT.md) — product vision and Version 1 scope
- [ARCHITECTURE.md](ARCHITECTURE.md) — high-level system architecture
- [ROADMAP.md](ROADMAP.md) — phased milestones
- [DECISIONS.md](DECISIONS.md) — architectural decisions already approved

## Independence from nrc-ai-agents

`nrc-social-agent/` is a separate, independent product living in the same repository as `nrc-ai-agents/` and `NRC Website/`. It must not import from, depend on, or share runtime configuration with `nrc-ai-agents/`. Do not reach into `nrc-ai-agents/.claude/skills` or its Python/Node tooling for this project's implementation. If a piece of shared logic seems tempting to reuse, copy or reimplement it here rather than creating a cross-project dependency.

## Approved stack (do not deviate without an explicit new decision)

- **Bot surface (V1):** Telegram Bot API
- **AI:** Claude API (Anthropic)
- **Storage & persistence:** Amazon S3 only — no database in Version 1
- **Hosting:** JustRunMy.App
- **Deployment:** GitHub
- **Language:** see [DECISIONS.md](DECISIONS.md) for the recommendation and justification

Do not introduce a database, message queue, or additional cloud provider in Version 1. Do not add Instagram/LinkedIn/Threads publishing code until their milestone is reached — only the extensibility seams for them.

## Current phase: Phase 1 / Milestone 11D.1 — Deploy Only `nrc-social-agent/` to JustRunMy.App

As of 2026-07-27, once an execution reaches `READY_FOR_DISPATCH` (Milestone 9), a new `src/publisher/` domain (generic contract + registry) and `src/publisher/instagram/` adapter, orchestrated by `src/execution/dispatch_service.py`'s `ExecutionDispatchService`, perform the system's first real, irreversible, publicly-visible side effect: an actual Instagram post. See [README.md](README.md)'s "Instagram Publisher Adapter and Dispatch Lifecycle" section for full detail; see [DECISIONS.md](DECISIONS.md) entry 10 for the four permanent decisions this milestone records.

**Official Meta documentation reviewed 2026-07-27** (developers.facebook.com only — no tutorials, no deprecated Basic Display docs): the three-step publishing sequence, the five container `status_code` values (including `PUBLISHED` as a real, queryable terminal state — the one fact that makes conservative ambiguous-outcome reconciliation possible at all), that `media_publish`'s returned id is distinct from the container id, both login/auth models, current Graph API version `v25.0`, and standard Graph API error codes.

**Repository media reality verified before implementing the API mapping, per this milestone's own explicit instruction**: only `image/jpeg` is analyzable today (`src/ai/analysis_service.py`'s `_ANALYZABLE_MEDIA_TYPES`), so only a single-image post is currently reachable — despite the output type being named `instagram_reel_caption`. This required **zero upstream contract change**: `resolve_media_mode()` (`src/publisher/instagram/models.py`) derives the real Instagram container mode from `MediaAssetReference.media_type`, never from `output_type`.

**The critical acceptance criterion — never publish more than once — is enforced by three mechanisms, not one**: an OCC-protected claim/lease (`ExecutionManager.claim_dispatch()`), checkpoint-before-call ordering for the one irreversible step (`PUBLISH_REQUESTED` is durably persisted *before* `publish_media()` is ever called, using the pre-transition in-memory snapshot so the call happens exactly once — see `dispatch_service.py`'s own docstring for exactly how), and conservative ambiguous-outcome reconciliation (one read-only container-status check; if it can't produce positive evidence, the execution becomes a permanent, non-retryable failure requiring manual operator intervention — never a second blind attempt). This system deliberately claims **at-most-once**, not exactly-once, delivery, because Meta's API provides no idempotency key that would make a stronger claim honest.

**Explicit publish authorization, not automatic-on-approve**: PRODUCT.md/ROADMAP.md were checked first (per this milestone's own mandatory instruction) — ROADMAP.md's Phase 3 goal mentions "actual publishing to Instagram on Approve" but explicitly defers "exact UX to be decided at this milestone." Given the introduction of a real irreversible side effect, the decision made here is a dedicated "Publish to Instagram" button, never inferred from approval alone; `dispatch_authorization` is persisted before the first Meta call, and `/retry` can resume but never create it.

**Continuing the pointer-clearing deferral pattern a third time**: `ExecutionService.create_execution()`'s existing `clear_pointer_on_success` parameter is now passed `False` when Instagram publishing is enabled (chaining into dispatch), and `ExecutionDispatchService` clears the pointer only once dispatch finally succeeds — mirroring the identical Milestone 8→9 deferral, and, per that same precedent, a *permanent* dispatch failure also leaves the pointer untouched so `/status`/`/retry` keep working through the ordinary active-pointer path.

**Flagged, not silently resolved**:
- Container-creation ambiguity is deliberately treated as *ordinarily retryable*, not with the same conservative-reconciliation treatment as publish ambiguity — an orphaned, unpublished container is harmless (self-expires in 24h); a duplicate live post is not. The two risks are not symmetric, so they are not handled identically.
- `external_media_id`/`permalink` are unrecoverable when a publication is confirmed only via reconciliation (Meta exposes no container→media reverse lookup) — a documented, accepted limitation; the execution still correctly reaches `COMPLETED`.

Also new this milestone: `/retry`'s eighth pending-operation value (`"publication_dispatch"`); execution schema v2 (`checkpoint`/`lease`/`platform_state`/`result`/`failure`/`dispatch_authorization`, all backward-compatible with v1); a new, disabled-by-default `INSTAGRAM_PUBLISHING_ENABLED` feature flag plus `META_GRAPH_API_VERSION`/`INSTAGRAM_ACCOUNT_ID`/`META_ACCESS_TOKEN`/`INSTAGRAM_MEDIA_URL_TTL_SECONDS`/`INSTAGRAM_CONTAINER_POLL_INTERVAL_SECONDS`/`INSTAGRAM_CONTAINER_POLL_TIMEOUT_SECONDS`/`DISPATCH_LEASE_SECONDS`/`META_REQUEST_TIMEOUT_SECONDS` (all placeholder-only in `.env.example`, all optional except the two credentials, and only when publishing is enabled). `httpx` is now a direct dependency (previously only transitive, via `anthropic`/`python-telegram-bot`) — no genuinely new third-party dependency was introduced. All automated tests use a fake Meta HTTP client and fake S3; no real Instagram post is ever made, no production credentials exist anywhere in this repository. When implementation continues:

- Follow [ARCHITECTURE.md](ARCHITECTURE.md) for component boundaries.
- Follow [ROADMAP.md](ROADMAP.md) for what belongs in which milestone — do not pull forward work from a later phase (e.g. Instagram publishing) into the Telegram MVP.
- Record any new or revised architectural decision in [DECISIONS.md](DECISIONS.md) rather than only in code or commit messages.

**Milestone 11A (2026-07-27) adds three independent fixes/additions, none touching a real Meta credential or making a real Meta API call:**

**Planning consistency rule**: `src/ai/content_plan_validation.py` now rejects any plan whose priority-1 output's `OUTPUT_TYPE_REGISTRY` entry has `supports_generation=False` — closing a latent bug (found during Milestone 11's planning investigation, not by a user) where `instagram_feed_caption` could be planned as priority-1 and permanently crash `draft_generation_service.py` later. Enforced entirely at the existing validation layer (`_validate_output_types_and_priorities()`), inheriting the existing one-bounded-regeneration-attempt-then-permanent-failure retry behavior for free — zero new service-layer code. Unsupported output types remain registered and selectable at any non-priority-1 slot; nothing was deleted.

**Explicit placement contract (Option B)**: `output_type=instagram_reel_caption` never reliably described actual Instagram placement (a single approved JPEG — the only media type reachable today — always publishes as a Feed image, never a Reel). Rather than splitting `output_type` itself (which would have touched Milestones 5/6's shipped schemas/prompts), `src/publication/models.py` now resolves `{channel, placement, media_mode}` once, at package-build time (`resolve_placement()`, called from `service.py`), and persists it on the package (publication schema v2, additive/backward-compatible). `src/publisher/instagram/publisher.py` now consumes `PublicationPackage.resolved_placement()` instead of re-inferring placement from the raw media type at publish time. Historical v1 packages (`placement=None` on disk) migrate lazily — `resolved_placement()` derives the same answer in-memory, never writing back to storage — package immutability is fully preserved. The reviewer-facing label reviewers see changed from "Instagram Reel caption" to "Instagram caption" (`content_plan_models.py`'s `display_name`) — presentation-only; Claude's planning prompt still sees the distinct `output_type` enum values regardless of display-name wording.

**Read-only Instagram diagnostics**: a new `/instagram_status` command (implemented with an underscore — Telegram bot commands reject hyphens) reports three independent, never-conflated health concepts: **application healthy** (always true, never depends on Meta), **Instagram configured** (credentials present), and **Instagram ready** (configured + valid token + correct permissions + verifiable account — the only concept a live Meta call ever affects). `src/publisher/instagram/diagnostics.py`'s `InstagramDiagnosticsService.check_status()` runs a short-circuiting, read-only sequence using two new `MetaHttpClient` operations (`debug_token()`/`get_account_identity()`, both plain GETs) — it never creates a container, polls one, or calls `publish_media()`, requires no active workflow, and creates or mutates no execution/publication record. No new configuration variable was introduced; startup still succeeds with `INSTAGRAM_PUBLISHING_ENABLED=false`, and diagnostics report that cleanly. Logging is limited to stage-reached/boolean-outcome; the access token, raw Graph responses, presigned URLs, captions, and hashtags are never logged.

**Milestone 11B (2026-07-27) implements a tightly controlled, operator-only workflow for the first real Instagram publication this system will ever perform — fully built and tested, but not yet exercised with real credentials (see the completion report's "Manual actions required from the operator").**

**No second publish implementation.** `/instagram_test_publish` → `ControlledLiveValidationService` (`src/execution/live_validation.py`) locates one eligible, approved, single-JPEG-Feed publication via the existing ownership-safe active-workflow pointer (never a new S3 listing capability), renders a safe confirmation preview, and — only after a second, distinct, one-time-use "Confirm live publication" callback — calls the *exact same* `ExecutionDispatchService.authorize_and_dispatch()` Milestone 10 already built. This module imports neither `InstagramPublisher` nor `MetaHttpClient` (verified by a structural test); the only change `dispatch_service.py` needed was one new optional `dispatch_context` parameter, merged into `dispatch_authorization` only the one time it's first created, carrying safe provenance (`mode="controlled_live_validation"`, operator id, confirmed-at timestamp, masked account fingerprint).

**Durable confirmation state, extending the execution domain rather than adding a new one.** A confirmation preview persists an `AWAITING_CONFIRMATION` record in the target execution's own `metadata["live_validation"]`, via a new OCC-protected `ExecutionManager.set_live_validation_state()` — reusing the execution domain's existing etag/conditional-write pattern. `confirm()` re-validates everything a second time (operator, token, expiry, execution status/checkpoint/attempt, a SHA-256 package digest, masked account fingerprint, fresh Instagram readiness) before consuming the confirmation via the same OCC write, guaranteeing two concurrent confirm callbacks can never both reach dispatch (see DECISIONS.md entry 12).

**A second, independent operator gate**: `INSTAGRAM_LIVE_TEST_OPERATOR_IDS` (optional, empty by default, never required at startup) is checked in addition to — never instead of — the general `TELEGRAM_ALLOWED_USER_IDS` allowlist. An ordinary authorized bot user is never automatically trusted to perform a real live publication.

**Scope deliberately narrow**: only a single JPEG Feed image is eligible (Reels remain out of scope even though the adapter supports them internally). `/retry` needed zero new code — `dispatch_authorization` is already a standing, execution-scoped authorization per Milestone 10's own design, so an ordinary `/retry` resumes a controlled-live-validation-originated dispatch through a retryable pre-publish failure without a new confirmation (verified by a dedicated test). Every test uses fakes; `tests/conftest.py` adds a session-wide autouse fixture that raises on any real `httpx.get()`/`httpx.post()` call, so no test can ever reach Meta's real API regardless of what credentials happen to be present. See README.md's "Controlled Instagram Live Validation" section and `docs/INSTAGRAM_LIVE_VALIDATION.md` for the full design and operator runbook.

**Milestone 11D (2026-07-27) added this project's standard deployment mechanism, `.github/workflows/deploy-social-agent.yml` (monorepo root, styled to match the NRC Website's own `deploy-production.yml`); Milestone 11D.1 (2026-07-27) corrected it to deploy only `nrc-social-agent/`, not the whole monorepo.**

This repository has three independent projects on one `main` branch. The workflow uses `git subtree split --prefix=nrc-social-agent` to generate a synthetic commit containing only this project's own tree, at the root (never nested, never with "NRC Website/"/"nrc-ai-agents/" present) — that commit, not `HEAD`, is what's pushed to JustRunMy.App's `deploy` branch. This was empirically verified in a sandbox before writing the workflow, not assumed: `git subtree split` requires full checkout history (`fetch-depth: 0`) to work correctly; it must run from the repository's toplevel, not from a `working-directory: nrc-social-agent` step (the job's install/test/Docker-build steps use that working-directory; the subtree/push steps deliberately don't); pushing a raw commit SHA requires a fully-qualified `refs/heads/deploy` destination (`<sha>:deploy` alone is rejected by git); and — most importantly — the split is deterministic (same source history + prefix always produces the same commit SHA, even from an independent fresh clone with no cache), which is exactly what makes ordinary forward deployments fast-forward safely without `--force`, while a genuine rollback to an older commit is correctly rejected as non-fast-forward (mitigated by preferring revert-and-redeploy over a forced push, matching the website workflow's own established rollback philosophy).

Deployment secrets changed from three (`JUSTRUNMYAPP_GIT_USERNAME`/`_PASSWORD`/`_REPO`, concatenated into a URL by the workflow) to a single `JUSTRUNMYAPP_GIT_URL` holding the complete, pre-built deploy URL — chosen specifically because constructing a URL from separate parts would require the workflow to URL-encode a password itself to stay safe against special characters, while a single secret has no such risk. Credentials are never printed, never traced (no `set -x` around the step that uses them), and the temporary remote is removed via a `trap ... EXIT` so cleanup fires on both success and failure. `paths`-filtered to `nrc-social-agent/**` (plus the workflow file itself) so unrelated monorepo changes never trigger a deployment. **A genuine prerequisite gap was found and reported, not silently worked around**: `nrc-social-agent/` has zero commit history in this monorepo as of this milestone, so a real run's subtree-split step will fail until at least one ordinary commit under this directory exists — this milestone does not commit anything on the project's behalf, per the standing "do not commit" constraint. **Still structurally independent of Instagram operational validation**: never calls `/instagram_status`/`/instagram_test_publish`, never validates Meta credentials, never touches Telegram. See `docs/DEPLOYMENT.md`'s "GitHub Actions deployment pipeline" section for the full setup and first-run walkthrough.
